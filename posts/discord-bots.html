two discord bots and the loop they share

  1. the loop
  2. Lespy: xp for saying thanks
  3. rejs: who's online

i've written two discord bots that have nothing to do with each other on paper, and they turned out to be the same program. Lespy hands out XP for saying thanks. rejs watches a game server and reports who joins and leaves. both boil down to the same loop: watch something, remember what changed, tell the right channel.

the loop

Lespy: xp for saying thanks

Lespy is a Python bot on discord.py with SQLite behind it, built for a community server. the rule is small: if a message contains one of a few trigger words ("ty", "thanks", "thank you") and it replies to or mentions someone else, that person gets 1 XP. thanking yourself gets you nothing. the point is to reward whoever actually helped, not whoever talks the most.

# condensed from bot.py: a thank-you only counts when it points at someone else if message.reference: replied_to = await message.channel.fetch_message(message.reference.message_id) if replied_to.author == message.author: # thanking yourself return user = replied_to.author elif message.mentions: user = message.mentions[0]

levels get harder as you climb. the XP needed for the next level is level * 2 * multiplier, clamped between a minimum and a maximum, with a level cap on top. every number (trigger words, multiplier, clamps, cooldowns) lives in one config file instead of the code, so tuning the pace of a server doesn't mean touching the bot.

required_xp = round(level * 2 * level_xp_multiplier) # 1.2 by default required_xp = max(min_level_experience, min(required_xp, max_level_experience)) # 10 .. 1000

there are three permission tiers, each in its own file, so a command's audience is decided by where it lives.

the part that took longest was the cooldown. without one, two friends can farm each other with "thanks" all day, so a sender gets 60 seconds between XP-giving messages. one thing i'd change now: the cooldown check runs before the message reaches the command handler, so someone on cooldown can't run commands until it expires. the fix is to process commands first and keep XP as its own concern:

# what i'd change it to @bot.event async def on_message(message): if message.author.bot: return await bot.process_commands(message) # commands never depend on the xp cooldown await award_thanks_xp(message) # xp logic, cooldown included, lives here

rejs: who's online

rejs is Node with discord.js and SQLite. FiveM game servers expose their player list as JSON, so the bot polls that endpoint once a second and compares it with the players it already has marked as in-game. the diff is two sets:

const currentIds = new Set(currentData.map(player => player.id)); const previousIds = new Set(previousData.map(player => player.id)); const joined = currentData.filter(player => !previousIds.has(player.id)); const left = previousData.filter(player => !currentIds.has(player.id));

new ids get a green "joined" line in the channel. missing ones get a red "left" line and a leave timestamp. the bot's status shows the live count from a second endpoint, like "64/128 players". the player table keeps names plus steam and discord identifiers, so a session traces back to an account and not just a display name.

!setservermonitor doesn't trust its arguments. before saving anything, it fetches the endpoint and refuses unless the answer is a JSON array:

const response = await fetch(playersUrl); if (!response.ok) return message.reply('Failed to fetch data from the provided IP address.'); const data = await response.json(); if (!Array.isArray(data)) return message.reply('The provided IP address does not return valid JSON data.');

on startup the bot copies every table into a timestamped backup and then clears the players table, so each run starts a fresh log without losing history. commands load from a folder, and !reload re-reads them without restarting the bot.

async function initializeDatabase() { await backupDatabase(); // every table into logs/backup_<timestamp>.db await clearDatabase(); // then this run starts with an empty players table }

the least tidy part is server restarts. the server goes away on a schedule, and a bot that treats every failed fetch as an outage either spams retries or gives up. rejs knows two ten-minute restart windows and backs off differently inside them, but the retry counters are module-level globals and the windows are hard-coded. before adding anything else i'd rebuild that as a small state machine: up, down, restarting.

what they share

poll, diff, persist, announce. SQLite is enough for both: one file, no server, and the state survives a restart, which is all a bot needs. neither one has to be a Discord bot. chat is just the interface people already keep open, a free notification channel with permissions and history built in.
