the half of every decision nobody was reading

item 1's own file said where to look first: profile which of the fields a squad computes actually get used. a squad's decision runs candidates(), which tries up to six routes and computes a flow field for each one just to see where it leads, then evaluate() scores every one of those candidates with a rollout, sorts them, and used to call plansFor() - another full field, per candidate - to build the actual per-member walking plan for all of them. only the winner is ever handed to a troop. the debug view, which lists every candidate's time and wall count in a table, never even reads the plans field; it only reads total and stageSlots. so roughly half of the fields a squad computed on every decision were computed for a candidate nobody was going to look at.

the fix is not a cache or a worker, it is making the unread half not happen: plans becomes a getter, computed once someone actually reads it, with the winner forced eagerly right after the sort so a caller that reads it a while later (a test that runs the world forward, for one) still gets the field as it stood at decision time, not a stale one:

// Scores every candidate for the given troops (the leader is the first) and returns them best first. Each entry's // plans are a full flow field, so they are computed lazily on first read: decide() only ever reads the winner's, // the debug view never reads any, only the oracle test wants every candidate's. evaluate(world: World, members: readonly Troop[]): Evaluated[] { const strength = this.strengthOf(members, world.stackAttackers) const scored = this.candidates(members[0], strength).map((candidate) => { const { total, stageTimes, stageSlots } = this.rollout.run(world, members, candidate.route, candidate.target) let plans: Map<number, Plan | null> | undefined const entry = { candidate, total, stageTimes, stageSlots } return Object.defineProperty(entry, 'plans', { enumerable: true, get: () => (plans ??= this.plansFor(entry, members, strength)), }) as Evaluated }) scored.sort((a, b) => a.total - b.total) void scored[0]?.plans // eager for the winner: caller may read it after the world (and these troops) moved on return scored }

21.0 ms against the old 23.8 ms, for the same benchmark part 2 used (10 squads, 50 troops, a 40x28 map). that is real and I would keep it, but it is not close to the 3 ms target, and I want to be honest about the gap: this only removes work that was already wasted, it does not touch the actual expensive parts (a field recomputed per squad per event with no cache, a squad's candidates searched fresh every time). the ideas that would close the rest of the gap - a field cache keyed by squad strength and map version, asking only the squads a change can affect, a worker - are still on the list, not done here.

a bug the oracle had been reporting since part 1

part 1's oracle runs every candidate plan of two hundred random maps through the real simulation and compares the planner's estimate to what actually happened. it has caught two bugs already (a missing slot rule, the narrow-passage wall pricing). item 4 asked me to go back to one seed it still could not explain: number 10069, one wall candidate, estimated 9.77 s, real 12.33 s, 24% off - inside the oracle's tolerance, so the test still passed, but a 24% miss on a single, simple candidate is not explained by noise.

I reproduced it directly rather than guess: built the same random scenario, ran the planner, then stepped the real simulation one tick at a time and logged every troop's state change. four balanced troops, one wall, one tower behind it. the wall died almost exactly on time (2.20 s real against 2.17 s estimated). the building did not: troop 0 reached it at 5.40 s as predicted, troop 1 a little after, but troops 2 and 3 - whom the estimate had arriving around 5.4-6.2 s along with the others - did not actually reach the building until 10.20 s and 10.43 s.

the reason was in how the rollout carries a squad from one stage to the next. within a stage it already modeled this correctly: a troop that loses the race for the nearest attack position gets bumped to a farther one, and the estimate adds the extra walking time for that - that machinery existed and was right. the bug was that this adjusted, later arrival was only used to compute that one stage's break time and then thrown away. the next stage's walk always started from the troop's original, un-relocated arrival at the current stage, as if the two troops that got bumped to farther wall positions had teleported back onto the fast path the moment the wall died. they had not; they were still walking to where the field had actually sent them.

const result = this.stageTime(world, members, arrivals, route, stage) times[s] = result.time arrivals = result.ready slotCounts[s] = this.lastSlots

the fix carries the real per-member time forward instead of recomputing it from scratch. stageTime() now returns the break time and a ready array, keyed by each member's original index, not its arrival rank - the rank-adjusted arrival for anyone who got bumped, the untouched arrival for anyone who did not:

// Returns the break time and, per member (by its original index, not arrival rank), the time it is free to // leave this stage: a member bumped to a farther attack position is not done until it actually walks there, // which the next stage's walk has to start from - not the time it would have arrived with no one in its way. private stageTime(world: World, members: readonly Troop[], arrivals: number[], route: Int32Array, stage: Stage): { time: number; ready: number[] } { const approach = route[stage.approachIdx] const byArrival = (a: number, b: number) => arrivals[a] - arrivals[b] || members[a].id - members[b].id const order = members.map((_, i) => i).sort(byArrival) if (world.stackAttackers) { // Everyone hits from the cell they arrive at: no positions to share out, nobody walks to another cell. this.lastSlots = members.length return { time: breakTime(stage.hp, order.map((i) => arrivals[i]), order.map((i) => members[i].type.dps), members.length), ready: arrivals } } const slots = this.freeSlots(world, stage, approach) // an approach cell that is a wall counts as free: it will be gone this.lastSlots = slots // The r-th troop to arrive takes the r-th nearest free position, which costs it a few more steps. const ready = arrivals.slice() const hitters = order .slice(0, slots) .map((i, rank) => { const arrival = arrivals[i] + this.slots.foundDepth[rank] / members[i].type.speed ready[i] = arrival return { arrival, dps: members[i].type.dps } }) .sort((a, b) => a.arrival - b.arrival) const time = breakTime( stage.hp, hitters.map((h) => h.arrival), hitters.map((h) => h.dps), hitters.length, ) return { time, ready } }

after the fix, seed 10069's own two candidates come out at 10.73 s and 11.87 s against a real 10.77 s and 12.33 s, both under 4% instead of 24%, and the planner now correctly prefers the walk-around route for that seed, which it had been picking wrong before on a bad estimate. run against the same two hundred maps plus two fresh sets that had not been looked at while writing the fix:

the slowest one sets the pace

item 5 was a one-line change the list suggested trying first: the field a squad uses to pick its route was costed with the squad's mean speed, and the file asked me to try the slowest member's speed instead and rerun the oracle. mean speed is an optimistic number - it prices a route as if the whole squad moves like its fastest members, when a mixed group actually moves like its slowest one:

const speed = Math.min(...members.map((t) => t.type.speed))

positions mode went from 199 of 200 picks within 5% to 200 of 200, and the single worst pick dropped from a ratio of 1.052 to 1.021. stacking mode, where units rarely relocate, did not change. all nine named scenarios gave the exact same numbers as before, because none of them happen to mix troop speeds inside one squad - which is itself worth knowing, since it means the scenario suite was not exercising this path at all, only the random-map oracle was.

a right-click menu, and the one thing it broke

the rest of this part is not about the planner at all. it is what came back once someone actually used the editor for a while, which finds a different kind of bug than sitting down and listing what's wrong ever does.

the first report was that picking a wall level, a building type or a unit type meant a trip to the side panel before every click, and asked for something closer to how a file manager's right-click menu works: click the map, get asked what to put there. the editor's four tools collapsed into one - Place - plus Spawn point, Erase and Select as before. a click with Place active opens a small popup at the cursor with three columns, and picking an entry places it on that cell and closes the menu:

it worked, and it broke something nobody had asked to change: painting a run of wall by dragging across cells. a wall was one of the three menu entries at first, and a menu that asks a question on every click cannot also support a drag, so laying a long wall meant clicking, choosing a level, clicking the next cell, choosing the level again, cell after cell. the report came back within one message of shipping it: "i cant place bulk wall." the fix was not to make the menu smarter, it was to admit that walls are a different interaction from buildings and units - painted in a stroke, not placed one at a time - and give them back their own tool, with a level <select> sitting right next to the button in the same toolbar row, so picking a level and dragging across cells works exactly like it did before the menu existed. buildings and units, which are placed one at a time anyway, stayed on the menu.

// The map-editing tool buttons, in their own row in the top bar below play/reset/speed. 'Place' opens the // context menu (src/ui/placeMenu.ts) on the next map click; 'Draw wall' paints on click and drag at the level // picked next to it - buildings and units are one-offs from the menu, but a run of wall is common enough to // want dragging, which a per-click menu can't give. export function buildToolbar(container: HTMLElement, editor: Editor): void { const buttons = new Map<Tool, HTMLButtonElement>() const refresh = () => { for (const [tool, button] of buttons) button.classList.toggle('on', tool === editor.tool) } for (const [tool, label] of TOOLS) { const button = document.createElement('button') button.textContent = label button.addEventListener('click', () => { editor.tool = tool refresh() }) buttons.set(tool, button) container.append(button) if (tool === 'wall') container.append(wallLevelSelect(editor)) } refresh() }

the same request moved the whole toolbar out of the side panel and into the top bar, on its own row below play, reset and speed, so the tool you are using and the transport controls are not competing for the same strip of the sidebar. it is a small layout change, but it is the kind of thing that is invisible until someone is actually clicking through it session after session.

two more things only real use found

the editor's "drop units" section had a plain dropdown showing just "Balanced" with no label, a button called "Drop at spawns" and another called "Clear units" - clear to me, because I built it, opaque to anyone reading it cold. the fix is unglamorous: a label above the dropdown ("Unit type to add"), the button renamed to "Add at spawn points" with a line under it explaining it drops at every spawn point and pointing at the Place tool's Unit entry for a single chosen cell, and a small "Will spawn:" list that actually shows what is queued, grouped by type, instead of asking you to remember what you clicked.

the next report sounded like the same feature was broken in the opposite direction: "added units doesnt spawn at start of run... added units always spawn at start." it took two rounds to land on what was actually meant. my first read was that timing was wrong; I reproduced it live, checked the recorded deploy time and the replay after a reset directly, and both were correct - a unit added mid-run got timestamped at the moment it was added, and a reset correctly replayed it at that same later moment. so the real complaint was the button's location, not its behavior, which the labeling fix above covers. then the second message clarified that no, the timing itself was the actual ask: added units should always be part of the run's opening batch, not a mid-run event that a reset faithfully reproduces at its original moment. that is a real change to what "add a unit" means, not a bug in the old sense - the old behavior was correct for what it was building, it just was not what either of us wanted once asked plainly:

// Drops one troop on each cell in both worlds, timestamped at the start of the run: it appears on the very next // step right now, and a reset (or replay) spawns it at t=0 with the rest, not wherever it was added mid-run. deployAt(cells: { x: number; y: number }[], troopType: string): void { for (const { x, y } of cells) { const event = { t: 0, troopType, x, y } this.scenario.deployments.push(event) this.classic.addDeployment(event) this.fresh.addDeployment(event) } }

the effect: a unit added five seconds into a run still appears right where you clicked, immediately, because a spawn time of zero is already in the past by the time the world checks it - but a reset now starts it alongside everything else instead of replaying the five-second wait. one existing test had encoded the old behavior as the thing being verified (compare a live mid-run session to its own replay and expect them to match); that assumption is exactly what changed, so I rewrote it to check the new one directly - a mid-run add gets spawnTime === 0, and a reset still replays deterministically at any frame rate, which is the part that still has to hold.

the last report was about the debug view's heat map, which part 2 described as showing seconds-to-finish colored across the map for the followed unit's type. it only ever drew on the panel the selection happened to be on - if you were following a unit in the "New" panel, the "Classic" panel next to it stayed plain green, even though both panels are running the same map with the same unit types and would benefit from the same picture. the two panels already have their own drawing layer each; the fix was to stop gating the heat map behind "is this the selected panel" and instead look up the same troop id in each panel's own world - both worlds are built from the same deployments in the same order, so the id lines up - and draw that unit's field against that panel's own walls. the route line and the white squad-radius ring stayed tied to the one panel actually being followed, since drawing a route for a differently-behaving copy of the same unit on the other panel would be showing something that is not true of it.

update(world: World, debug: Debug, seconds: number): void { const { heat, halos, routes, wallInfo, labels } = this.view if (!debug.enabled) { labels.visible = false return void this.clear([heat, halos, routes, wallInfo]) } labels.visible = true this.drawHalos(world, halos) const followed = debug.panel === this.panel && debug.troopId !== null ? world.troops[debug.troopId] : undefined this.drawWallInfo(world, followed?.isActive() ? followed : undefined) // Heat map: both worlds are built from the same deployments, so debug.troopId is the same unit in either one. // Shown on both panels (against each panel's own grid), not only the one the selection happens to be on. const heatTroop = debug.troopId === null ? undefined : world.troops[debug.troopId] if (heatTroop?.isActive()) this.drawHeat(world, heatTroop.type.speed, heatTroop.type.dps, heatTroop.type.id, seconds, heat) else this.clear([heat]) if (followed === undefined || !followed.isActive()) return void this.clear([routes]) this.drawRadius(world, followed, halos) this.drawRoute(world, followed.id, routes) }

the whole thing in one paragraph

three real fixes this time: a wasted half of every planning decision (fixed, though the real speed target is still 8x away), a 24% estimate miss that had been sitting inside the oracle's own passing tolerance until someone asked to explain it (fixed, root cause in one function that dropped a value it had already computed correctly), and a one-line change to which speed a mixed squad plans around (fixed, and it moved the worst pick from 1.052 to 1.021). none of that is what someone using the editor actually noticed first - what they noticed was a menu that made bulk wall-painting impossible, two unlabeled buttons, a spawn timestamp that meant something different than expected, and a heat map that only ever showed on one side. every one of those came from watching the thing get used, not from a list written in one sitting, and that is probably the more honest source of the next one.
